## 反馈循环及假设

命令：`python tools/diagnostics/run_offline_tests.py`，整个测试过程禁止真实 Frida attach/spawn。

新增 `tests/test_desktop_blank_relaunch.py`，直接经过实际 WmpfCdpBridge 重开、初始化与等待路径：

1. 原 TCP 保持连接、重新收到 setupContext 且初始化成功时，原版仍要求 TCP 连接代次增加，误报通道未就绪。
2. 全部初始化命令均超时，原版 finally 无条件设置 ready，产生假就绪。
3. 重开前未结束的初始化线程能污染重开后的状态。
4. 旧 context 线程第一个命令返回后，仍向新页面发送第二条命令。

最初 181 项测试有 3 项失败；追加旧 context 线程回归后 183 项测试有 1 项失败。修正后 183 项全部通过（3.312 秒）。

排名假设为：复用 TCP 但新页面握手被拒绝、旧异步初始化污染、新初始化失败却假就绪。已向用户说明排名与可证伪预测；离线证实代码确有这些缺陷，真实现场触发项待验证。

## 第一阶段候选修复（当时尚未发布；最终结果见后文）

- 将页面代次与 TCP 连接代次区分；重开立即隔离旧页面，可接受同一 TCP 上属于本次页面的新初始化。
- 初始化成功须收到 Runtime.runIfWaitingForDebugger 的成功回包，不能把全部超时当成功；之后仍由 backend 验证真实 globalSearch 路由。
- 主初始化及 context 初始化均捕获页面/连接/取消代次，禁止旧任务跨代发送命令或设置新页面状态。
- 记录连接建立、初始化成功/失败、关闭命令未确认、异步启动回包与失败时的连接状态。
- GUI 新增本地轮转日志 `data/logs/collector-runtime.log`，每份最多 2 MiB，保留 2 份备份；放在 .cache 之外，避免清缓存遇到正在打开的日志文件。
- 不增加页数上限，不跳过失败词，不更改价格、去重、1000 条分表及断点规则；不强杀微信，不退出登录。

15:24:28 的真实协议证据：

```text
PROTOCOL_REPLY outer_id=0 inner_id=1
PROTOCOL_REPLY outer_id=0 inner_id=2
PROTOCOL_REPLY outer_id=0 inner_id=3
```

旧版只按外层 op_id 匹配待完成请求，因外层为 0 丢弃了已返回的有效结果，因此误报超时。现在优先匹配 JSON 内层 id，缺少内层 id 时才回退外层；带 method 的通知不再消耗等待中的命令。新增真实编码/解码路径测试在旧实现报出超时，修复后通过。这是此次确认的程序缺陷，不是把 TCP 在线当成页面就绪。
