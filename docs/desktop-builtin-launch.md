# v13：内置正常小店启动入口

## 故障与原因

用户要求宿主崩溃后独立重开，不依赖文件传输助手窗口。
旧 URI 只成功提交给 ShellExecute，并不能在本机正常初始化小店；只有后台 PID 不能当作启动成功。
v12 的正常卡片路径又依赖可见的独立聊天窗口，窗口不在就不能自动恢复。

2026-09-10 只观察用户手动打开指定 lining李宁卡片的正常请求，确认该卡片最终调用 Weixin 原生启动调度函数。
没有读取其他聊天、记录凭据、复制聊天对象指针或修改身份验证。
测试发现不用保存店铺私有上下文，只用小店 AppID 和已存在的关键词搜索路由就能正常打开搜索页。

自动化关闭的方式也有差异：旧 WM_CLOSE 路径在现场连续重试仍得到空白页；改为小店窗口自身“关闭”按钮的 Invoke 后，相同启动器确认搜索页在约 4 秒内出现。
这支持原关闭方式与小程序实际退出不一致。不能仅因 HWND 消失就认定小程序状态已经销毁。
保留正常关闭等待及真实内容检测；缺少 Invoke 的旧提供程序使用 WM_CLOSE 后仍必须通过内容检测，不能绕过检查。

## 精确版本及接口

只允许 desktop_builtin._CONSTRUCTORS 中的完整 SHA256，不按版本字符串放行。

| DLL | 默认请求构造函数 | 正常启动调度 |
| --- | --- | --- |
| Weixin 4.1.13.63 | 0x7866f0 | 0x220a80 |
| Weixin 4.1.13.65 | 0x7869b0 | 0x220a80 |

请求大小 0xe8，原生构造函数设置所有默认字段；AppID 字符串指针 +8，entry route 字符串指针 +24，presence bits +0xe4 = 1|4。
保持 scene=1000 及所有其他原生默认值。调度函数不使用第一个参数，自行取得当前微信服务，入队前复制 const 请求。
.65 构造函数及调度函数已静态核对；.65 未在目标电脑实测，不宣称已完成端到端验证。

生产实现每次重新核对主进程、线程和文件哈希，短暂挂载主微信调用正常入口；保留缓冲区至启动观察结束，之后卸载脚本和会话。
不挂载冷 WMPF，不伪造初始化标记，不在未知版本强行调用；原后台采集通道仍必须通过已初始化宿主检查和新一代 CDP 页面检查。

## 生命周期与数据

释放旧采集会话 → 调用小店自己的关闭动作 → 确认旧窗口关闭 → 内置正常入口打开搜索页 → 连续三次确认可见搜索控件 → 建立受保护采集连接 → 验证新页面及搜索路由 → 继续当前关键词。

空白页、断线属于连接恢复，按 15/30/60/120 秒可取消等待重试，不消耗商品搜索的三次失败额度。
用户可停止，重新开始重新取得连接；真正的登录/安全验证/平台限制不自动绕过。
恢复时当前词从第一页重采并由原保存器去重；每个词读取服务端返回的全部分页，不增加页数上限。
不需要文件传输助手，不要求 lining 卡片常驻，也不需要把店铺凭据写入软件。

- 原生产集成探针 red：WM_CLOSE 后搜索内容连续未就绪，正确自动恢复等待；正式文件未改变。
- 改用小店关闭 Invoke 后，单次入口探针成功。
- `builtin_recovery_probe.py 49856 --fresh-host --collect` 完整通过：第一次正常搜索连接；停止旧小程序宿主 70644，新宿主 56976 首次空白页被识别，自动关闭重开后恢复 CDP；微信主 PID 49856 保持不变。
- 同一进程中 pause → clear cancel → start → open_search_page 成功。
- 测试词“可水洗单人榻榻米床垫”完整读取 18 页、171 个商品，最后一页 1 个，服务端确认末页；仅内存回调，无正式文件写入。

- 一次替换宿主仍会出现暂态空白页，但自动重试已通过。不承诺微信永不崩溃或所有版本零故障；本次验证目标是失败后不再要求用户点击聊天卡片。

诊断脚本仅位于 tools/diagnostics，不随便携包发布。运行结束释放全部控制器；观察用户启动的临时只读挂载也已移除。
