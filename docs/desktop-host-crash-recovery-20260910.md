# v10：宿主崩溃后的恢复边界

## 证据和范围

v9 在 2026-09-10 02:35–08:35 从第 813 个关键词处理到第 1541 个，共 729 个进度完成。第 1542 个“棉麻针刺织四件套”第 7 页超时后，正常李宁卡片已打开，但后续恢复仍失败。

Windows Application 1000/1001 确认 08:36:25、08:36:38、08:37:16、08:37:54 四个 WeChatAppEx 宿主分别崩溃：flue.dll + 0x19b887b，异常码 0x80000003。Report.wer 元数据与事件一致；档案只有 Report.wer，没有可用调用栈或 dump。本轮没有读取聊天/进程内存，也没有触发真实故障以强行复现该原生异常。

08:36:30 的 CloseApplet 超时及 reset_scene_patch 的 `script has been destroyed` 被旧代码吞掉；随后 dispatch_async 隐式 start，换宿主后仍沿用旧启动任务。连接恢复错误又消耗当前词重试次数，三次后自动暂停。09:08 用户手动继续时同词读取 19 页/184 商品；所以这次不是商品确实搜不到。

## 红测试与假设

命令：`python -m unittest discover -s tests -p test_desktop_host_crash.py -v`。

先执行 2 个最小启动故障回放，均 FAIL：宿主消失/脚本销毁后仍发送 LaunchApplet。随后添加通过真实 Listener → Backend 恢复调用链的三次失联回放，旧实现会产生用户所见的“三次失败，已暂停并保留断点”，而不是恢复同词。测试完全隔离真实 Frida、UI 和正式数据。

排名假设：

1. 旧启动事务中途跨宿主重连——已用回放确认。
2. 恢复失败消耗商品关键词重试，短间隔反复启动——已用真实 listener 路径回放确认。
3. 残留 ready/旧回调污染新连接——增加防御回归，验证不得假成功；不能据此认定它就是 flue.dll 崩溃原因。

## 实现

- Frida detached 事件作废原生连接、唤醒等待者、清理页面就绪状态；不记录 crash 对象或聊天内容。
- Close → reset → Launch → runtime refresh 绑定同一组脚本和 session。禁止事务内隐式挂载。发送前再检查连接，等待中新宿主死亡立即退出。
- Close 超时不是关闭成功。仅明确“session 未绑定/不存在”可以作为新会话正常启动；其他关闭/重置失败进入正常卡片恢复。
- 旧 session 的晚到 detached 回调不影响新连接。主动释放先摘除 session 身份，再 detach。
- 正常入口的恢复循环与关键词重试分离。退避 15/30/60/120 秒，后续封顶 120 秒；每次等待前释放失效连接，不进行 native RPC。正常首页和真实搜索页连续稳定才成功。
- 启动期原生连接失败也走同一条完整恢复，而不是复用坏连接三次后报错。
- 正常卡片存在但首页空白/窗口关闭未完成，以明确的 ShopBootstrapTimeout 进入恢复等待；不与卡片缺失等人工前置条件混同。
- 测试自动恢复期间启用停止按钮，取消事件在后台线程启动前建立，避免 Stop/Close 先于 backend 创建时丢失取消；测试不触发 CSV 导出。
- 不改价格、筛选、结果末页判断、保存规则、去重或断点。正常搜索失败仍有原有的有限重试；平台限制和需要登录/验证不无限重试。
- 没有卡片或独立文件传输助手窗口等非瞬时前置条件仍提示人工处理。不会退出主微信或读取其他会话。

## 防复发

根本的工程问题是原生连接生命周期和分页/关键词重试混在一起，低层命令可偷偷 start，调用者无法知道运行环境已经换代。今后新 native 命令必须遵守连接事务边界，恢复故障必须走独立恢复状态机，不能新增“吞异常后继续发命令”的分支。
