## 已确认的证据

- 原分页调用把等待商品接口的 Promise 放在 XWeb 的固定 5000 毫秒执行窗口内，返回 `TIMEOUT_ERROR`。短调用启动任务、随后轮询结果的实机验证已通过 6.4 秒等待及同一关键词完整分页；这不证明连接退出安全。
- 2026-09-09 10:29:06，原 WMPF PID 45408 在 `frida-agent.dll` 中崩溃。
- 2026-09-09 10:29:09，原 Weixin PID 24516 在同一模块、同一偏移 `0xfc891d` 中崩溃。异常码 `0xc0000409`，WER 异常数据 7。没有足够的调用栈证据进一步归因到某条 Frida 内部代码。
- 两次崩溃发生在诊断脚本报告成功并结束之后，因此只检查采集回调/脚本退出码会漏报故障。
- 在我们自己创建的独立 Python 进程中，简单挂载、卸载、分离后等待 45 秒未崩溃；控制端进程也退出后再等待 45 秒同样未崩溃。这只能排除最简单的必现卸载故障，不能证明微信环境安全。
- 原 `DesktopKeywordListener.stop()` 先卸载 backend，然后 join 采集线程；存在仍在发出原生命令时释放脚本的顺序风险。本地测试已锁定并修正这一顺序，但这还不是上述 native 崩溃的完整根因证明。

## 当前修改

1. 分页使用短命令启动异步任务，轮询完成；超时仅重试同一游标。失败不推进关键词断点。
2. 不再以固定 300 页为终止条件；同一词持续读取到微信返回 `hasMore=false`。305 页回归测试通过。
3. 正常“停止”只取消当前任务、唤醒 XWeb/CDP 等待并等待工作线程结束，不卸载原生连接、不关闭小店。
4. GUI 保留一个电脑版 backend；再次“开始”用新运行状态复用已有连接。临时搜索页故障优先重开搜索页而非重复 detach/attach。
5. 软件最终关闭时，先停止任务、等待启动/采集线程退出，再释放连接。原生 dispatch 与最终卸载受同一锁保护。
6. 被取消的 XWeb 回包必须报取消，不能把空回包视为成功。启动取消不弹启动失败窗口。
7. 微信重登后若只有后台宿主、尚未初始化小店，不再直接发送 XWeb 命令：提示先打开一个小店名片。已成功进入搜索页的宿主按 PID 与进程创建时间记录；同一个进程可在软件重开后复用，微信重启后的旧记录不可复用。

## 真实验证与边界

`tools/diagnostics/desktop_survival_check.py` 监督 `desktop_restart_smoke.py`：

- 不写正式商品目录或断点。
- 同一词读到第 4 页主动停止，再复用同一连接从该词开始，读到实际末页。
- 每轮先验证超过 5000 毫秒的异步结果。
- 最终释放连接、控制端退出后，继续监测原微信与 WMPF 进程 60 秒；不接受自动重启的新 PID 代替原进程存活。

2026-09-09 首次申请本轮测试被安全检查拒绝，未绕过。用户随后明确回复“允许”，才执行以下实机验证。

### 获得授权后的记录

- 11:01:39、11:02:18、11:02:56：尚未打开真实小店的后台宿主触发 `flue.dll + 0x19b887b` 的原生断言（0x80000003）；微信主进程 41200 未退出。这是初始化阶段失败，不是分页失败。初版监督脚本没有正确转发子进程标准输出，已修正；Windows 事件日志与进程句柄检查仍捕获了失败。
- 通过用户先前发到文件传输助手的现有小店名片，正常打开小店；没有发送消息。实际仍复用带 `--web-translate` 标记的宿主，因此不能简单把该标记当成“错误进程”。对照支持“小店服务未初始化”的判断，但没有原生完整堆栈来锁定断言内部业务含义。
- 11:11:55–11:13:10，微信 41200、WMPF 29712：第一轮读到第 4 页、40 商品主动停止；第二轮同词从头读到微信返回的第 18 页末页，共 171 商品。两轮 6.5 秒 Promise 均成功返回，未受原 5000 毫秒窗口影响。正式商品回调仅打印计数，不写正式数据。
- 11:13:10 释放连接、控制端退出；原 PID 41200 与 29712 在随后 60 秒仍存活，监督检查退出码 0。
- 新增初始化保护的两个本地测试修改前失败、修改后通过。随后执行 `desktop_survival_check.py --entry-only`：第一次从可见小店启动成功并记录已验证宿主，关闭全部连接；第二次创建新的 backend，在小店窗口已关闭的情况下使用同一 PID/创建时间记录启动成功。两次均输出 `ENTRY_READY`，控制端退出码 0。
- 上述独立连接验证结束后，同样通过原 PID 存活 60 秒检查，未发现新增应用崩溃事件。

## 未解决/不能承诺

- 上述受控实机检查没有再复现延迟崩溃；不是对所有微信状态、所有机器和无限时长的保证。
- 微信刚重登或小程序宿主重启后的首次初始化，目前需要先点开一个小店名片。此次实现了安全保护，没有宣称已实现该状态下无人工初始化的冷启动。
- 用户说“不报错”不能解释为吞掉网络、登录、验证或平台无结果异常。非正常失败应保留数据与当前词断点；不能伪造采集完成。
- 普通单元测试无法证明已注入的第三方原生进程不会崩溃，必须保留原 PID 的延迟存活检查。
